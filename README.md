# never-afk

`never-afk` is a lightweight menu bar utility that keeps your machine active only when it has
actually gone idle. It waits through a quiet period, confirms that no human input has happened
recently, and then sends a minimal synthetic key press.

The result is simple: fewer false wake-ups, less unnecessary input, and a predictable background
tool that can be limited to the exact days and time ranges where you want it running.

## Highlights

- Menu bar utility with a compact settings window
- Configurable quiet period and idle confirmation period
- Configurable synthetic key presets plus custom platform key codes
- Weekly schedule ranges with multiple windows per day
- Runtime status in the UI and tray
- Start at login support on supported platforms
- Local-first behavior with no telemetry, no network features, and no input logging

## How It Works

`never-afk` follows a cautious cycle before generating any synthetic input:

1. Wait for the configured `quiet period`.
2. Observe the system for the configured `idle confirmation period`.
3. Cancel the cycle immediately if human input is detected.
4. Send a minimal synthetic key press only if the machine is still idle.

When a weekly schedule is enabled, the automatic cycle only runs inside the configured schedule
ranges. Outside those ranges, the engine sleeps until the next relevant start or end boundary
instead of polling constantly.

## Main Features

### Synthetic key selection

Choose from built-in presets such as function keys and modifier keys, or provide custom platform
key codes when you need more control.

### Weekly schedule ranges

Create as many schedule ranges as you need:

- different ranges on different weekdays
- multiple active windows on the same day
- exact start and end times for each range

This is useful when you only want `never-afk` active during specific working blocks instead of the
whole day.

### Persistent tray status

The tray/menu bar reflects the current engine state and can optionally show the timestamp of the
last synthetic event.

### Privacy-first behavior

`never-afk` is intentionally small in scope:

- no telemetry
- no remote services
- no input history
- no activity logging

## Platform Notes

- macOS and Windows are the intended targets.
- Linux is not supported.
- macOS safe presets currently cover `F13` through `F20`.
- `F21` through `F24` remain available on Windows.
- macOS can still use supported custom key codes through the advanced input path.

## Development

```bash
npm install
npm run build
cargo test --manifest-path src-tauri/Cargo.toml
npm run tauri dev
```

Use a current stable Rust toolchain. The repository includes `rust-toolchain.toml` to make that
expectation explicit.

## Releases

GitHub Releases are published when you push a supported release tag:

- `version-x.x.x` for the stable channel
- `beta-x.x.x-beta.n` for the beta channel
- `canary-x.x.x-canary.n` for the canary channel

Example:

```bash
git tag version-0.1.0
git push origin version-0.1.0
```

Before tagging a release, make sure the version matches in all three places:

- `package.json`
- `src-tauri/Cargo.toml`
- `src-tauri/tauri.conf.json`

The release workflow checks that automatically and refuses to publish if the tag version and
manifest versions do not match.

### Release signing

The in-app updater uses Tauri's signed updater artifacts. GitHub Actions needs these values before
it can publish working updater bundles:

- repository variable `NEVER_AFK_UPDATER_PUBLIC_KEY`
- repository secret `TAURI_SIGNING_PRIVATE_KEY`
- optional repository secret `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`

Generate the updater key pair with the Tauri signer and keep the private key outside the repository:

```bash
pnpm tauri signer generate -w ~/.tauri/never-afk-updater.key
```

The base64-wrapped public key generated by `--ci` is intentionally committed in
`src-tauri/tauri.conf.json` because Tauri's bundler needs it when generating updater manifests. The
same public key should be stored in the repository variable; the release workflow accepts either that
wrapped value or a raw minisign public key block, normalizes it, and verifies that it matches
`tauri.conf.json`. The private key content or path is only for local builds; in CI, store the private
key content in the GitHub secret.

macOS releases use a `Developer ID Application` certificate and Apple notarization. GitHub Actions
needs the following repository secrets in addition to the updater key:

- `APPLE_CERTIFICATE`: the password-protected `.p12` export encoded as a single-line Base64 value
- `APPLE_CERTIFICATE_PASSWORD`: the `.p12` export password
- `APPLE_API_PRIVATE_KEY`: the App Store Connect `.p8` private key
- `APPLE_API_KEY`: the App Store Connect Key ID
- `APPLE_API_ISSUER`: the App Store Connect Issuer ID

The workflow writes the `.p8` only to the runner's temporary directory, imports the `.p12` through
Tauri's temporary keychain support, verifies the distributed app bundles, and publishes the GitHub
Release only after both platform jobs pass. None of these private values belong in the repository.
Local macOS release bundles require the matching `Developer ID Application` identity in the login
keychain.

Installed builds check their GitHub release channel automatically at most once per week while the
engine is enabled. Automatic checks only look for a newer signed manifest; downloads and installs
still require an explicit user action. Manual checks remain available from the app UI and the status
bar menu.

Release assets currently target:

- macOS Apple Silicon: `DMG` for manual installs plus the signed `.app` updater archive
- Windows x64: `EXE`
- in-app updater bundles generated by Tauri

These builds are intended for personal convenience rather than full commercial distribution. The
macOS app contained in the DMG and updater archive is Developer ID signed, notarized, and stapled.
The updater archive is also protected by Tauri's separate Minisign signature. Windows SmartScreen
may still show a warning because the Windows installer is unsigned.

The first update from an older ad-hoc-signed build changes the application's macOS code identity.
macOS may therefore require removing and re-adding `never-afk` in **Privacy & Security →
Accessibility**, followed by one app relaunch. Later Developer ID-signed updates keep the stable
bundle and Team ID identity, so that one-time migration should not repeat.

If the workflow cannot create or update a release, enable GitHub Actions workflow permissions with
repository write access for `GITHUB_TOKEN`.
